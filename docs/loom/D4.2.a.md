# D4.2.a cellsCovering picks a geohash precision the index does not hold

The spec for a fix in `client/src/lib/geohash.ts`. The rule it implements is
[§ 4.2 and § 10 of the compile rules](../search/compile-to-vespa.md), which specify a precision floor; this task
makes the helper obey it.

## Problem

`cellsCovering(view, max)` walks precision from 6 down to 1 and returns the first precision whose cell count fits a
budget (`max`, default 8). A `#g` filter is an **exact tag match**, so a cell is only useful at a precision the items
actually carry. The coarsest precision in the index is 4. Any cell coarser than that matches nothing.

A 25 km box needs 12 cells at precision 4 and a 40 km box needs 20, both over the budget, so the helper coarsens past
4 and returns cells no item carries. Measured on the live relay, 2026-11-01:

- `{"kinds":[39999],"#z":[FOOD],"#g":["dp3"],"search":"include:spam"}` → **0**
- `{"kinds":[39999],"#z":[FOOD],"#g":["dp3w"],"search":"include:spam"}` → **32**

This is shipped. `ListKindSearch.tsx:579` calls `cellsCovering(area)` with the default and hands the result to
`fetchAreaEvents`, which uses it as `#g` on the NIP-52 kinds and on event-list items. At city zoom and wider both
filters match nothing. It is masked because `fetchAreaEvents` also queries by town name when it has one, so results
look thin rather than empty; with an area and no town the geo half returns nothing at all.

**Why the tests did not catch it.** `geohash.test.ts` asserts that the returned cells _overlap_ the view and that
there are no more than eight of them. The geometry was never wrong. Nothing asserted that the precision is one the
data holds, so the widening-view test passes today by returning precision-2 cells for a Texas-sized box — cells no
event in the index carries.

**Why a floor alone is not enough.** With a floor of 4, a view larger than roughly 6° × 3° needs more cells than is
reasonable to send: a Texas-sized box is about 2,300 cells at precision 4, and the relay sheds a filter around 5,000
tag values (`docs/search/audit-2026-10-22.md`). Such a view cannot be served by `#g` at all, and the honest answer is
no cells rather than cells that match nothing. That makes an empty result meaningful, which the caller must then
handle: `fetchAreaEvents` builds `"#g": cells` unconditionally, and an empty tag array is a filter that matches
nothing — the same failure by a different route.

## For whom

Anyone looking at the map in `ListKindSearch`, where area search is the feature, and the compile rules, which already
specify the floor this helper will now honour.

## Decision

1. **A precision floor, not a budget.** `cellsCovering` walks 6 → 4 and never returns a cell coarser than 4. The
   floor is a named constant with a comment saying it is a property of the data, verified against the live relay and
   against the Austin event in the existing test, not a mathematical truth.
2. **`max` becomes a cap, not a coarsening budget.** Default 32, which admits precision 4 for the views that need
   it — 12 cells for a 25 km box, 20 for a 40 km one — and rejects precision 5 for them, since precision 5 would
   need 168 cells for the same 25 km box and the only count measured against the relay is at precision 4. Erring
   coarse is the point: the bug was asking for a precision the data may not hold, so a precision with evidence
   behind it beats a finer one without. It also keeps the filter small.

   | View                   | precision | cells |
   | ---------------------- | --------- | ----- |
   | downtown Austin, 0.02° | 6         | 15    |
   | 25 km around Chicago   | 4         | 12    |
   | 40 km around Chicago   | 4         | 20    |
   | Texas, 10° × 12°       | none      | 0     |

3. **Above the cap, no cells.** When even precision 4 exceeds `max`, return `[]`, meaning _no geohash filter can
   serve this view_ — never _no results_.
4. **The caller drops the filter rather than sending an empty one.** `fetchAreaEvents` omits both `#g` filters when
   `cells` is empty, leaving the town-name queries to answer; with no cells and no town it returns nothing without a
   request.

Precision 7 and finer are left alone: items carry 7, but 6 is present too and finer cells only multiply the filter
for no gain, so the top of the walk stays at 6.

## Done when

- `cellsCovering` never returns a precision coarser than 4, at any view size.
- A 25 km box around Chicago returns precision-4 cells including `dp3w`, the cell measured to hold 32 items.
- A view too wide for the cap returns `[]`, and `fetchAreaEvents` sends no `#g` filter when it does.
- `geohash.test.ts` asserts the precision floor and the empty case. The widening-view test is rewritten: it asserted
  a cell count the floor makes impossible, and it was green while the behaviour was broken.
- `npm test` and `npm run lint` pass.

## Out of scope

- **The post-filter.** Callers already keep only the items inside the true radius or view bounds; this task does not
  change that, and the cells remain a recall filter rather than the answer.
- **The index's precisions.** That items are tagged at 4 and finer is a fact about the data written by importers and
  other clients. Brainstorm-UI only reads `g` tags — `encodeGeohash` is module-private — so nothing here can change
  what is present, and the floor is a constant to revisit if that changes.
- **The other five index gaps** in § 10 of the compile rules. They need relay or schema work; this one is a client
  bug.
