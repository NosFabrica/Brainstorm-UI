# A6.1.a Build the list code as one ES module

A story of A6.1, the Tapestry connector (nousclawds4/tapestry `docs/loom/A6.1.md`; its decision is `engineering-team/decisions/tapestry-connector/0001-where-the-connector-runs.md` there). The connector checks and drafts lists with the code List Management runs here, pinned to a commit, never a copy. That code imports through Vite's `@/` alias, so outside this repo it needs a build.

## What it changes

- `client/src/lib/listTools.ts`: one entry that re-exports the list code other programs use: `listCheck`, `listDraft`, `listPrompt`, `listImport` and `dictionaryConcepts`.
- `vite.lists.config.ts` and `npm run build:lists`: Vite's library mode builds that entry, and everything it imports, into one ES module at `dist-lists/lists.js` (ignored by git). It runs in Node, with the aliases resolved and `nostr-tools` bundled in, so it imports nothing.
- **No deployment's env is baked in.** The env prefix matches nothing, so the config the code reads falls back to the repo's JSON, the same on every deployment. The modules already guard `window`, so the caller needs to supply nothing.
- `tsconfig.json` type-checks the new config.

The app's own build is unchanged.

## Tests

`client/src/lib/listTools.build.test.ts`, in Node rather than jsdom, builds the module into a temporary folder and imports it as a program outside the repo would. Then:

- the build is one file that imports nothing;
- it exports what `listTools` does;
- `checkHeader` gives the source's answer on a header that publishes as it is, one with no `d`, a field name the form won't take, and a hint the import drops;
- `checkItem` gives the source's answer on a whole item, a blank title, a missing required field and an undeclared field;
- `listAuthoringPrompt` writes the same prompt.

CI runs it with the rest of `npm test`, so a change that breaks the build, or makes it answer differently, fails there.
